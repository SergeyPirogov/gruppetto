# Соціальне, етап 2: живі групові заїзди й гонки

Статус: чернетка архітектури · Автор: Serhii Pirohov · 2026-11-09
Залежить від етапу 1 (`docs/specs/social-phase1.md`): вхід, профіль, Supabase.

## Навіщо

Найчастіше «немає» у відгуках зі Zwift — живих людей поруч: групових заїздів, гонок, пачки. Боти й драфтинг уже є;
бракує справжніх райдерів у тій самій пачці.

## Що входить

1. **Заїзди за розкладом** (`events`): маршрут, кола, час старту, тип (груповий з ведучим / гонка), категорії.
2. **Лобі заїзду:** «старт через 12 хв · 7 записалось», список учасників, вхід за 10 хв до старту, спільний відлік.
3. **Живі райдери в заїзді:** видно в 3D, на мінікарті, в таблиці «Попереду», драфтинг від них такий самий, як від ботів.
4. **Груповий заїзд з ведучим:** ведучий — живий організатор або бот-пейсер на заданих Вт/кг; хто відірвався
   вперед, тому показує «почекай групу» (як у Zwift «stay together» — без телепортації на етапі 2).
5. **Гонка:** спільний старт, результати по фінішу, категорії A–D (з етапу 1), підсумок у лідерборді заїзду.
6. **Боти добивають групу** до 5–8 райдерів, якщо людей мало (налаштування заїзду).

## Що не входить

- Підтримка будь-коли (Zwift «world» з тисячами людей). Лише кімнати на заїзд.
- Фізика на сервері й повний захист від підробленого клієнта (див. «Чесність»).
- Голосовий/текстовий чат (хіба що готові реакції 👍🔥 — опційно, в кінці).
- Приватні заїзди за посиланням — етап 3 разом із клубами (але схема не має цьому заважати).

## Архітектура

Сервер **не рахує фізику**, лише пересилає. Кожен браузер рахує свого райдера сам (як зараз: `advance()` у
`js/app.js`) і раз на секунду надсилає свій стан. Чужих райдерів між оновленнями плавно ведемо самі.

```
браузер A ──стан 1 Гц──▶  кімната заїзду  ──▶ браузери B, C, …
          ◀──стани інших──      (relay)
```

### Транспорт: спершу Supabase Realtime, з можливістю замінити

- Етап 2a — **Supabase Realtime broadcast**, канал `event:<event_id>`. Уже є після етапу 1, вхід той самий.
- Увесь код транспорту — за одним інтерфейсом у `js/live-transport.js`, щоб потім замінити на
  **Cloudflare Durable Objects** (одна кімната = один об’єкт, WebSocket) без змін решти коду:

```ts
// js/live-transport.js (тип для ясності; сам файл — звичайний JS з JSDoc)
export interface LiveTransport {
  join(eventId, me): Promise<void>;     // me: { id, name, color, stripe, category }
  send(state): void;                    // свій стан, ≤ 1 раз на секунду
  onState(cb): void;                    // cb(riderId, state, receivedAt)
  onPresence(cb): void;                 // хто в кімнаті: прийшов / пішов
  onControl(cb): void;                  // від сервера/організатора: старт, фініш, «зупинити»
  leave(): void;
}
```

Реалізації: `SupabaseTransport` (етап 2a), `FakeTransport` для тестів (кілька «браузерів» в одному процесі).

### Повідомлення (стан райдера)

Компактний JSON (≈ 100 байт), раз на секунду:

```json
{ "t": 1731180000123, "d": 5123.4, "v": 9.82, "p": 245, "c": 88, "h": 151, "l": 0.3, "e": 0, "f": 0 }
```

`t` — час відправки (мс, годинник клієнта; синхронізація — нижче), `d` — дистанція від старту, м, `v` — м/с,
`p` — Вт (3-с середнє, як на табло), `c` — каденс, `h` — пульс або 0, `l` — смуга, `e` — 1 якщо в ERG/симуляторі
(див. «Чесність»), `f` — час фінішу, с від старту (0 = ще їде).

Ім’я, колір, вага й категорія — лише при вході в кімнату (presence), не щосекунди.

### Скільки повідомлень і як не платити забагато

Кожен отримує стан кожного: N райдерів → N·(N−1) доставок на секунду.
20 райдерів × 1 год ≈ 1.4 млн доставок. На платному тарифі Supabase це відчутно (тариф і ціни — перевірити перед
запуском, вони змінюються).

Зменшення, від простого:
1. **За відстанню:** райдери в межах ±300 м від мене — щосекунди; далі — раз на 5 с. Реалізація на стороні
   відправника неможлива (broadcast усім однаковий), тому в 2a — **кожен шле щосекунди лише коли поруч хтось є,
   інакше раз на 5 с** (поруч = за останнім відомим станом інших). Це вже ріже рахунок у 2–4 рази на розтягнутій гонці.
2. На Cloudflare (етап 2b) — фільтр на сервері кімнати: кожному лише ті, хто поруч, рідше — решта.
3. Ліміт кімнати: 30 райдерів (налаштування заїзду).

Перехід на Cloudflare — коли місячні доставки перевищать включене в тариф Supabase. Метрика — лічильник у `track()`:
`live-room-size`, `live-minutes`.

### Синхронізація часу і старт

- При вході клієнт вимірює зсув годинника: 3 запити часу сервера (`select now()` через RPC), береться медіана
  з поправкою на півзатримки. `serverNow() = Date.now() + offset`.
- Старт гонки — `starts_at` у таблиці `events`; відлік у всіх від `serverNow()`, тож однаковий з точністю ~100 мс.
- Відлік і «GO!» — наявний `ride.race.countdown` (`js/app.js`), лише джерело часу інше.
- Хто увійшов після старту групового заїзду — стартує з хвоста групи (дистанція останнього); у гонку після старту — не можна.

### Чужий райдер у грі

Стан приходить раз на секунду, а кадри — 60 на секунду. Між оновленнями:
- **Екстраполяція:** `d = d_last + v_last · (now − t_last)` з поправкою на нахил (не потрібна на етапі 2a).
- **Корекція без ривків:** коли приходить новий стан, похибку розподіляти за 0.5–1 с (не стрибати).
- Немає оновлень 5 с — райдер напівпрозорий; 30 с — прибрати (presence скаже, що пішов).

Структура — та сама, що в ботів (`ride.bots`), щоб рендер, мінікарта, «Попереду», `packDraft` і `bunch.js` працювали
без окремих гілок коду:

```js
// у ride: remotes — живі райдери, оновлюються з мережі, а не з фізики
{ id, name, color, stripe, dist, v, power, lane, pedal, remote: true, category, lastAt }
```

Що змінити в `js/app.js`:
- драфтинг: `const pack = [...ride.bots, ...ride.remotes, ...pacer]` (зараз `ride.bots` + пейсер, ~рядок 1335);
- боти бачать живих як «колеса» (`wheels` у циклі ботів) — тоді пачка ботів чіпляється й за людей;
- рендер/мінікарта/профіль/«Попереду»/таблиця гонки — додати `ride.remotes` там, де зараз `ride.bots`;
- фізика ботів **не** чіпає `remote: true`.

Боти в живому заїзді рахуються **у одного клієнта** — в організатора (або першого в кімнаті) — і розсилаються як
звичайні учасники з `bot: true`. Інакше в кожного були б свої боти в різних місцях. Якщо він пішов — роль переходить
наступному (presence, найменший id).

### Дані (Supabase)

```sql
create table events (
  id uuid primary key default gen_random_uuid(),
  title text not null,
  kind text not null check (kind in ('group','race')),
  route_id text not null, route_version text not null, laps smallint not null default 1,
  starts_at timestamptz not null,
  pace_wkg numeric(3,1),                 -- груповий: темп ведучого
  categories char(1)[] ,                 -- гонка: дозволені категорії, null = усі
  max_riders smallint not null default 30,
  fill_bots smallint not null default 0, -- добити ботами до N
  host uuid references profiles,
  created_at timestamptz not null default now()
);
create table event_signups (event_id uuid references events on delete cascade, user_id uuid references profiles on delete cascade,
  category char(1), primary key (event_id, user_id));
create table event_results (event_id uuid references events on delete cascade, user_id uuid references profiles on delete cascade,
  position smallint, time_s numeric(8,1), avg_power smallint, avg_hr smallint, wkg numeric(4,2), flags text[] default '{}',
  primary key (event_id, user_id));
```

- `events` створює поки лише адмін (власник проєкту) — роль через `profiles.role` або список у функції.
- Результати пише `submit_event_result(event_id, …)` з перевірками з етапу 1 + «фініш не раніше, ніж
  `довжина / 25 м/с` після `starts_at`».
- Канал Realtime приватний: підписатись можна лише з записом у `event_signups` (Realtime Authorization / RLS на
  `realtime.messages`).

### Чесність

Клієнт сам каже, де він, тож підкрутити його можна. На етапі 2:
- **На сервері** — результати перевіряються, як на етапі 1 (стелі Вт/кг, швидкість, тривалість).
- **У клієнтів** — кожен перевіряє чужі стани: стрибок `d` більший за `v·Δt + 30 м`, `v` > 25 м/с, `p/вага` вище стелі
  на 30 с поспіль → райдер позначається «?» і **не дає драфту** та не враховується в місцях наживо (у підсумку
  все одно вирішує сервер).
- **Симулятор у гонці заборонено**; у груповому — дозволено, з позначкою.
- Повна серверна фізика (сервер отримує лише потужність і сам рахує швидкість) — етап 2b+, якщо буде проблема.

### Мережа погана

- Втратив зв’язок — їдеш далі сам (усе локально, як зараз), інші «застигають» і зникають через 30 с.
- Повернувся — знову в кімнаті, твоя дистанція правильна (вона завжди своя).
- Запис заїзду й FIT не залежать від мережі взагалі.

### Інтерфейс

- Лобі: вкладка «Заїзди» — найближчі події (сьогодні / тиждень), «Записатись», нагадування (Notification API, опційно).
- Перед стартом: екран очікування з відліком, список учасників з категоріями, «Розминка» — можна крутити вільно.
- У заїзді: таблиця гонки (`race-board`) з людьми й ботами; людей відрізняє прапорець/значок, ботів — 🤖.
- Після: результати заїзду (місце в категорії, час, Вт/кг), посилання на лідерборд події.

## Тести

- `tests/live-core.test.mjs`: екстраполяція й корекція без ривків, перевірки правдоподібності чужих станів,
  зсув годинника (медіана), вибір «господаря ботів».
- `FakeTransport` + Playwright: 3 вкладки в одному контексті, один заїзд; усі бачать одне одного на тих самих місцях
  (±5 м), драфтинг від живого працює, відключення й повернення однієї вкладки, фініш і результати.
- Навантаження: скрипт на Node, що імітує 30 клієнтів у кімнаті 10 хв (через справжній Supabase у тестовому проєкті),
  міряє затримку й кількість доставок.

## Готово, коли

- [ ] Двоє людей на різних комп’ютерах бачать одне одного в одному заїзді, позиції збігаються в межах кількох метрів.
- [ ] Драфтинг від живого райдера такий самий, як від бота.
- [ ] Відлік старту однаковий у всіх (розбіжність < 0.5 с).
- [ ] Боти однакові в усіх учасників; при виході господаря ботів вони не зникають і не стрибають.
- [ ] Обрив мережі на 1 хв не зупиняє заїзд і не псує запис.
- [ ] Симулятор не може фінішувати в гонці; неправдоподібний результат не потрапляє в підсумок.
- [ ] Заміна `SupabaseTransport` на `FakeTransport` не потребує змін поза `js/live-transport.js`.
- [ ] Метрики кімнати (`live-room-size`, `live-minutes`) пишуться, щоб видно було, коли час на Cloudflare.

## Етап 2b (після 2a, якщо приживеться)

- `CloudflareTransport`: Durable Object на кімнату, WebSocket із hibernation, фільтр «хто поруч» на сервері,
  валідація станів на сервері (стрибки, швидкість).
- Опційно — серверна фізика: клієнт шле лише потужність, каденс і пульс, кімната рахує швидкість і позицію.

## Відкриті питання (замовчування в дужках)

3. Нагадування про заїзд: пуш у браузері чи лише лист? (пуш, якщо дозволив; лист — ні)
